# 도어트림 AI 자동예측 시스템 — 현상 진단과 해결 방안 (Fable 답변)

작성일: 2026-10-05 · 대상: 사내 "도어트림 AI 자동예측 시스템 — 프로젝트 전체 과정 정리" 문서와 ChatGPT 제안(PerSAM/Find3D/SAM 3)에 대한 답변
구현물: `doortrim-atlas` (이 저장소) — 오프라인 파이썬 패키지, 합성 데이터로 전 과정 검증 완료

---

## 1. 한 줄 결론

**①번(부품 자동분류)은 "경계를 찾는 문제"가 아니라 "과거 차종의 라벨을 옮겨 붙이는 문제"로 바꿔야 풀립니다.**
사내 DB(36차종 · 70완제품 · 1,904바디, 표준부품코드 95.8% 분류 완료)는 그 자체가 이미 최고의 학습 데이터이고,
이 도구는 그 DB만으로 — GPU, 가중치 다운로드, 외부 연동 없이 — 신규 스킨을 부품 단위로 나누고 중량까지 예측합니다.

## 2. 왜 지금까지의 시도가 모두 50% 상한에 걸렸는가

| 시도 | 결과 | 공통 원인 |
|---|---|---|
| SAM2 (사진 + box prompt) | IoU 50.5% (독립 부품 0.7~0.9, 이어진 패널 0.1~0.5) | 음영 렌더링에 **경계 신호가 없으면** 어떤 분할 모델도 못 나눔 |
| 밝기 Region-Growing | 41.5% | 같은 이유 — 밝기가 같은 두 패널은 한 덩어리로 번짐 |
| 메쉬 연결성(거리) | 15~18% | CATIA STL 은 face 단위로 쪼개져 "틈"이 부품 경계와 통계적으로 구분 안 됨 |
| 곡률 | 7~15% | 이어진 패널은 경계에서 오히려 더 평평함 — 가정 자체가 역방향 |
| B-rep Face 경계 | 실패 | 부품 하나가 3,338 면 — 면은 설계 세부단위이지 부품 단위가 아님 |
| Sketch/Relations/피처 부모 추적 | 실패 | 양산 데이터는 결과물만 남고 이력 소실; 디자인 모델은 이력은 있으나 "어느 조각이 한 부품"인지 안 적혀 있음 |

이 여섯 가지는 모두 **"입력 스킨 안에서 경계를 찾는다"** 는 한 문제의 변주입니다. 매끈하게 이어진 패널 사이의 경계는
사진에도, 메쉬에도, 피처 이력에도 **정보로 존재하지 않습니다.** 없는 정보는 PerSAM 이든 SAM 3 이든 Find3D 든
어떤 모델을 가져와도 복원할 수 없습니다. 그래서 "오라클(사후 최선 선택)" 조차 58.1% 에 머물렀던 것입니다.

반면 **"이 자리가 어느 부품인가"** 는 정보가 아주 풍부합니다. 도어트림의 부품 배치는 차종을 넘어 거의 일정하고,
그 배치가 36차종 × 좌우 분량으로 라벨과 함께 DB 에 있습니다. 메인트림/어퍼트림의 경계가 안 보여도,
"과거 차종들은 벨트라인에서 이 비율 아래를 메인트림이라 불렀다"는 사실은 옮겨 올 수 있습니다.

## 3. 구현한 방법 (아틀라스 기반 라벨 전이)

### 3-1. 아틀라스 구축 (`build-atlas`)
1. 완제품(차종+좌우) 하나의 모든 Body STL 을 읽어 **조립 상태로 합치고**, 면적 비례로 표면 점 25만 개를 샘플링합니다.
   메쉬 연결성은 전혀 쓰지 않으므로 face 단위로 쪼개진 STL 이어도 영향이 없습니다.
2. PCA 로 주축(길이 u, 높이 v, 깊이 w)을 잡고, 차량 좌표계 관례(X 뒤, Z 위, 실내는 y=0 쪽)로 부호를 정합니다.
   좌/우 도어는 **거울상 변환(det=−1)까지 허용**해 같은 배치로 맞춥니다.
3. **가시성 필터(z-buffer)** 로 실내에서 보이는 A면 점만 남깁니다 — 솔리드의 뒷면·리브·다른 부품에 가려진 면은 제거.
   이것이 "양산 솔리드"를 "디자인 스킨"과 같은 형태로 만들어 줍니다. 솔리드/서피스 여부와 법선 방향 오류는 자동 판정·보정.
4. 가시 점 3만 개를 정규화 좌표(u,v ∈ [0,1], w 는 트림 길이 단위)로 저장하고, 점마다 기하 특징 16개
   (위치, 법선, 바탕면 대비 돌출, 두 스케일의 법선 변화·높이 범위, 평면성, 외곽까지 거리)를 계산해 둡니다.
5. 코드별 통계(전체/가시 면적, 가시 bbox, 중량, 재질, 가시 비율)를 함께 저장합니다 → 중량 예측과 "숨은 부품" 추정에 사용.
6. 두 번째 아틀라스부터는 8가지 부호 가설(±u, ±v, ±w) 중 **기존 아틀라스들과 챔퍼 거리가 가장 작은 것**을 고르므로,
   차종마다 좌표계가 달라도 자동으로 맞습니다. 첫 아틀라스만 미리보기 PNG 로 눈 확인(`cabin_dir` 로 수정 가능).

### 3-2. 신규 스킨 분할 (`segment`)
1. 스킨 STL(파일 1개 또는 Geometrical Set 별 조각 폴더)에서 점 20만 개 샘플링 → 8가지 자세 가설 → 라이브러리와 비교해 선택
   → 가시성 필터(숨은 작업 서피스 제거) → 4만 점 사용.
2. 챔퍼 거리로 **유사 아틀라스 상위 k=8개** 선택(사이즈·비율이 비슷한 과거 차종이 자동으로 뽑힘).
3. 아틀라스마다: 유사변환→아핀 ICP 로 전역 정렬 후, **부품별 국소 정렬** — 각 부품(큰 패널 제외)의 깊이맵 고역통과 패치를
   스킨 깊이맵과 정규상관(NCC) 블록매칭해 ±6셀(≈±70 mm) 이동량을 찾습니다. 차종 간 암레스트·베젤 위치 차이를 흡수합니다.
   (전역 격자 비강체 보정도 `nonrigid: "grid"` 로 남겨 두었습니다. 합성 실험에서는 부품별 방식이 mIoU 0.60→0.69 로 더 좋았습니다.)
4. 스킨 점마다 아틀라스 이웃 10개의 라벨을 거리 가중 투표 → 확률. 아틀라스 간에는 유사도 가중 평균.
5. 점 분류기(ExtraTrees, 아틀라스 점으로 학습)의 확률과 **로그선형(전문가 곱)** 으로 융합합니다. 선형 평균은
   "8개 아틀라스가 제각각 자리에 둔 작은 부품"의 희석된 표를 분류기가 못 이기지만, 곱은 이깁니다(세일 가니시 IoU 0.14→0.66).
6. 가벼운 그래프 평활(1회) → **부품의 평소 크기 기준** 조각 정리(그 코드의 평균 점유율 × 0.1 보다 작은 섬만 흡수).
7. 점 라벨을 면(face)으로 옮기고(조각 폴더면 보이는 면적 기준 다수결), 부품별 면적·bbox·신뢰도를 계산합니다.

### 3-3. 사이즈·중량·원가 예측 (`segment` 에 포함, `predict.py`)
* 사내 기존 "형상유사도 zero-shot 매칭"과 같은 철학이되 입력이 스킨이므로 **보이는 면적(A면)** 을 기준으로 아틀라스의
  같은 코드 부품과 비교합니다(아틀라스 쪽도 같은 가시성 필터로 계산한 가시 면적을 저장하므로 기준이 같습니다).
* 세 추정치의 중앙값: ① 최근접 3건 가중평균(기존 방식), ② 코드별 면적밀도(g/mm²) 중앙값 × 면적, ③ 로그-로그 회귀(폭주 방지 클램프).
* 재질은 최근접 부품들의 다수결, 단가표(`--cost-table 재질,kg당단가.csv`)가 있으면 재료비도 계산.
* **스킨에 안 보이는 부품**(브래킷·클립·리브류)은 유사 차종 상위 k개의 BOM 을 유사도 가중 평균 — "비슷한 차종 절반 이상이 가진 부품"만.

### 3-4. 평가 (`evaluate`)
차종 하나를 빼고 아틀라스/분류기를 만든 뒤, 뺀 차종의 가시 점구름을 **임의 회전·이동**해 신규 스킨처럼 넣고
부품별 IoU 를 잽니다. 사내 보고서의 SAM2 50.5% 와 같은 지표입니다. 70 완제품이면 70폴드 10~20분.

## 4. 검증 결과 (합성 데이터)

실데이터는 반출 불가이므로 배치·치수·곡률·곡면 단차·좌표계·좌우가 조금씩 다른 합성 도어트림(9부품)으로 검증했습니다.

| 조건 | 점 정확도 | 부품 IoU 평균 | 큰 부품(메인/어퍼/암레스트/포켓/풀핸들) | 작은 평면 부품(베젤·그릴·가니시) |
|---|---:|---:|---|---|
| 14대, 13폴드 | 94.1% | 0.775 | 0.89 ~ 0.99 | 0.46 ~ 0.74 |
| 8대(아틀라스 7개), 다른 시드 | 95.0% | 0.805 | 0.91 ~ 0.99 | 0.42 ~ 0.85 |

* 메인트림/어퍼트림 경계(사내 핵심 미해결): IoU 0.89 / 0.90.
* 보류 차종 중량 예측(8부품): 오차 중앙값 13% (단일 STL) / 14% (조각 폴더). 사내 기존 17~28%.
* 자세: 13폴드 모두 임의 회전·거울상에서 올바른 가설을 선택(선택된 가설 번호가 다양함에도 IoU 유지).

**주의:** 합성 데이터는 실제보다 규칙적입니다. 실데이터에서는 큰 부품은 비슷한 수준, 작은 부품은 더 낮을 수 있습니다.
반대로 실데이터에는 합성에 없는 강한 단서(스티치 라인, 재질 경계의 미세 단차, 파팅라인 홈)가 있어 더 좋을 수도 있습니다.
**진짜 숫자는 사내에서 `evaluate` 한 번이면 나옵니다.**

## 5. 보고서의 4개 질문에 대한 답

**Q1. 디자인 초기 모델에서 "어느 작업조각들이 하나의 최종 부품"인지 자동 식별하는 알려진 방법이 있는가?**
일반해는 없습니다. CATIA 는 "부품"이라는 개념을 서피스 모델링 이력에 저장하지 않습니다. 실무에서 쓰이는 단서는
(a) Geometrical Set 의 **이름·구조**(디자이너가 부품별로 Set 을 나누는 관례가 있으면 그것이 정답), (b) 최종 외관면은
보통 **Join(접합)** 피처 하나로 묶이고 그 입력들이 한 부품의 조각들이라는 점, (c) trim/split 의 중간 결과물은 숨김(Hide)
상태라는 점입니다. 보고서의 stitch_xshell 240개가 바느질 땀이었듯, 피처 개수나 면적으로 부품을 세는 방법은 맞지 않습니다.
→ 이 도구는 그 식별을 **아예 필요 없게** 만듭니다. 조각이 수천 개여도 표면 점만 보고, 라벨은 과거 차종에서 가져옵니다.
   다만 (a)가 지켜진 모델이면 `--per-set` 으로 Set 별 STL 을 넘겨 조각 단위 다수결을 켜면 경계가 거의 정확해집니다.

**Q2. CATIA COM 에서 피처의 부모(입력)를 추적하는 공식 방법은?**
범용 `Parents/Fathers` 는 자동화(VBA/COM) 레벨에 없습니다(CAA C++ 의 CATISpecObject 에만 있음). 대신 **타입별 입력 속성**은
있습니다: `HybridShapeJoin.GetElement(i)`, `HybridShapeSplit.Elem / Cutting`, `HybridShapeTrim.GetElem(i)`,
`HybridShapeBlend.FirstCurve/SecondCurve/FirstSupport/SecondSupport`, `HybridShapeFillet.FirstElem/SecondElem`,
`HybridShapeOffset.ElemToOffset`, `HybridShapeExtrapol.ElemToExtrapol/BoundaryElem`, `HybridShapeFill.GetBound(i)`.
각 속성은 `Reference` 를 돌려주고 `.DisplayName` 으로 부모 이름을 얻습니다. 즉 "Shape 를 타입 판별 → 타입별 속성 호출"
로 의존 그래프를 그릴 수는 있습니다(수백 줄 작업). 그러나 Q1 대로 그 그래프가 "부품"을 알려 주지는 않으므로
투자 대비 효과가 낮습니다. (COM 안정성 문제 — CNEXT 2개 실행, SetRealColor 반복 — 는 색칠 대신 STL 로 내보내 외부에서 색을
입히는 이 도구의 흐름이면 발생하지 않습니다.)

**Q3. 매끈하게 이어진 여러 부품을 사진/3D 만으로 구분하는 더 나은 방법?**
경계가 없는 형상의 분할은 **대응(correspondence) 기반 라벨 전이**가 정석입니다: 의료영상의 multi-atlas segmentation,
Kalogerakis 등(2010)의 라벨된 예시 기반 3D 메쉬 분할, 코세그멘테이션(co-segmentation) 계열이 모두 "예시에서 라벨을 옮긴다"는
구조입니다. 딥러닝 쪽(PointNet++/Point Transformer 를 사내 데이터로 학습)도 같은 정보를 쓰지만 70개 완제품으로는 데이터가
부족해 과적합 위험이 크고, 어차피 배치 사전지식이 성능을 좌우합니다. 이 도구는 그 비딥러닝 버전으로, 데이터 70건에서
바로 동작하고 설명 가능하며(어느 차종의 어느 부품에서 라벨이 왔는지 JSON 에 남음) 오프라인입니다.
ChatGPT 가 제안한 PerSAM(참조 이미지 기반)·SAM 3(텍스트 프롬프트)·Find3D(점구름+부품명)는 모두 **입력에 시각적 경계가 있을 때**
강한 도구이고, 가중치 반입·GPU·(SAM 3 는) 접근 승인이 필요합니다. 나중에 "추가 투표자"로 섞을 수는 있지만 이어진 패널 문제의
해법은 아닙니다.

**Q4. 지금 입력만으로 도달 가능한 정확도 상한과, 입력을 바꿔야 하는가?**
상한은 "과거 차종 간 배치의 일관성"으로 정해집니다. 합성 실험 기준 큰 부품 0.9 안팎, 작은 평면 부품 0.5~0.8 입니다.
경계가 디자인 선택인 곳(메인/어퍼 분할 높이 등)은 어떤 방법도 "과거 평균"이 상한이고, 요구하신 "유사한 결과"에는
충분합니다. 더 올리려면 입력에 **최소 정보 1개**를 더하면 됩니다 — 디자인팀에 "Geometrical Set 1개 = 부품 1개(또는 Set 이름에
부품명)" 만 요청하면 조각 단위 다수결로 경계 정확도가 바로 올라갑니다. 사진(렌더링)을 더 요구할 필요는 없습니다.

## 6. 실데이터 적용 시 예상 이슈와 대처

| 이슈 | 대처(이미 반영) |
|---|---|
| STL 이 face 단위로 쪼개짐, 틈 | 연결성 미사용(점 샘플링) — 영향 없음 |
| 좌표계가 차종마다 다름 / 좌우 도어 | 8가설 자동 선택 + 거울상 허용. 첫 아틀라스만 미리보기로 확인 |
| 솔리드 뒷면·리브가 섞임 | 가시성 필터 + 솔리드 판정 시 뒷면 제거(법선 뒤집힘 자동 보정) |
| 가려져서 안 보이는 부품(보고서 "1,000픽셀" 문제) | 애초에 스킨에 없는 부품이므로 분할 대상에서 제외되고, 유사 차종 BOM 으로 중량만 보충. 아틀라스에 코드별 가시 비율 저장 |
| 디자인 모델의 작업 서피스 수천 개 | 보이는 면만 남기고 전부 무시. Hide 된 요소는 CATIA STL 출력에서 제외 |
| 표준부품코드 93종 중 희귀 코드 | 라벨 전이는 상위 k 아틀라스에 있는 코드만 투표하므로 자연히 희귀 코드는 비슷한 차종이 있을 때만 등장 |
| 라벨 오류가 있는 아틀라스 | `evaluate` 의 fold_*.png 로 역추적 가능(어느 아틀라스에서 라벨이 왔는지 segmentation.json 에 기록) |
| 큰 STL 로 느림 | 샘플 수 설정으로 조절, 아틀라스 구축은 중간 저장(--append) |

## 7. 권장 로드맵

1. (사내, 1일) 설치 → `demo` → `inspect-db`/`make-manifest` → `build-atlas` → `previews` 눈 확인 → `train` → `evaluate --max-folds 10`.
2. (사내, 1일) 전체 70폴드 평가, 코드별 IoU 표를 사내 보고서의 SAM2 표와 나란히 비교. 낮은 코드는 fold PNG 로 원인 분류
   (라벨 오류 / 배치 편차 / 가려짐 / 희귀 코드).
3. (사내, 반나절) GL3_PE2 디자인 1차 모델 STL 내보내기(`scripts/catia_export_skin.py --per-set` 권장) → `segment` →
   `prediction_summary.md` 를 기존 원가·성능 규칙 모듈에 연결(알렉스 가이드).
4. (디자인팀 협의) "Set 1개 = 부품 1개" 관례 요청. 적용되면 조각 다수결(`piece_vote_threshold`)로 경계 정확도 상승.
5. (선택) 결과를 사람이 수정한 이력(`classification_decisions` 와 같은 승인 함수)을 아틀라스에 되먹임 — 수정된 신규 차종을
   `build-atlas --append` 로 추가하면 다음 차종부터 반영됩니다. 이것이 "기존 학습을 바탕으로" 가 계속 좋아지는 구조입니다.
